# reMarkable Notebook File Format

> Reverse-engineered from firmware **3.26.0.68** via SSH investigation.
> Last updated: 2026-03-22.

This document covers the internal notebook file format used by reMarkable tablets, with particular attention to cross-device compatibility pitfalls. It is intended for the reMarkable hacking community -- developers building tools that create, modify, or deploy notebook files.

If you have a Paper Pro and can help fill in the gaps, see [Help Wanted: Paper Pro Testing](#help-wanted-paper-pro-testing) below.

## Notebook File Structure

All notebook data lives under:

```
/home/root/.local/share/remarkable/xochitl/
```

Each notebook is identified by a UUID and consists of several files at the top level plus a subdirectory for page data:

```
{uuid}.content     -- JSON, cPages v2 format, zoom/orientation settings
{uuid}.metadata    -- JSON, type="DocumentType", visibleName, timestamps
{uuid}.local       -- JSON, { contentFormatVersion: 2 }
{uuid}/            -- subdirectory for page data
  {pageId}.rm      -- binary v6 lines file (strokes/layers per page)
{uuid}.thumbnails/ -- PNG thumbnails (generated by device, not deployed)
```

### .content

The `.content` file is the primary structural document. It uses the **cPages v2** format and contains:

- **`cPages`**: ordered list of page UUIDs with CRDT metadata
- **`customZoomPageWidth` / `customZoomPageHeight`**: always `1404` and `1872` (see [Universal Coordinate System](#universal-coordinate-system))
- **`orientation`**: `"portrait"` or `"landscape"`
- **`zoomMode`**: zoom/fit settings
- **`coverPageNumber`**: which page to use as the notebook cover thumbnail

### .metadata

Standard xochitl metadata:

- **`type`**: `"DocumentType"` for notebooks
- **`visibleName`**: the user-facing notebook title
- **`lastModified`**: Unix timestamp (milliseconds) as a string
- **`parent`**: UUID of the parent folder, or `"trash"` / `""` for root

### .local

A small JSON file that declares the content format version:

```json
{ "contentFormatVersion": 2 }
```

### Page data ({uuid}/)

Each page has a `{pageId}.rm` file containing the binary v6 lines format -- all stroke data, layers, and pen metadata for that page. Page IDs are UUIDs referenced from the `.content` file's `cPages` array.

### Thumbnails ({uuid}.thumbnails/)

PNG thumbnail images generated by the device. These are **not** required for deployment -- the device regenerates them automatically. Do not bother deploying these.

## Universal Coordinate System

This is one of the most important (and initially confusing) aspects of the notebook format.

**ALL devices use 1404x1872 for `customZoomPageWidth`/`customZoomPageHeight` in `.content` files.** This was confirmed by inspecting all 40 notebooks on a Paper Pro Move device -- every single native notebook, including ones created directly on the PPM, uses 1404x1872.

This means the notebook coordinate system is universal. A notebook created on an RM1 has the same coordinate space as one created on a PPM. The device handles scaling from the 1404x1872 coordinate space to its physical display resolution at render time.

```
Notebook .content coordinates:  always 1404 x 1872
     |
     v
Device renders at native resolution, scaling as needed
```

This is distinct from template coordinates, which ARE device-specific (see next section).

## Template vs Notebook Dimensions

This is where things get confusing, and it is important to understand the distinction.

**Templates** use device-specific coordinate systems for rendering:

| Device | templateWidth | templateHeight | Notes |
|--------|--------------|----------------|-------|
| RM1/RM2 (rm) | 1404 | 1872 | Same as notebook coords |
| Paper Pro (rmPP) | 1620 | 2160 | Higher resolution |
| Paper Pro Move (rmPPM) | 814 | 1454 | Template coords; physical panel is 954x1696 |

**Notebooks** always use 1404x1872 regardless of device.

Why the difference? Templates are rendered directly by the template engine, which needs to know the exact pixel dimensions of the target display. Notebooks, on the other hand, go through a rendering pipeline that includes zoom/pan/scale transformations, so they use a canonical coordinate space that gets mapped to physical pixels at display time.

The practical upshot: when you deploy a `.content` file, always use 1404x1872 for `customZoomPageWidth` and `customZoomPageHeight`. When you deploy a `.template` file, use the device-specific dimensions.

## Empty .rm v6 Files Are Device-Specific

This is the sharpest cross-device compatibility edge we have found. Empty `.rm` files -- the binary blobs for pages with no user strokes -- are **not identical across devices**.

| Device | Empty .rm size | Deploy strategy |
|--------|---------------|-----------------|
| PPM (rmPPM) | **423 bytes** | MUST be pre-deployed for correct rendering |
| RM1/RM2 (rm) | **408 bytes** | Device creates its own on first page access; do NOT deploy |
| Paper Pro (rmPP) | Unknown | UNTESTED -- see [Help Wanted](#help-wanted-paper-pro-testing) |

The 15-byte difference between PPM and RM1 is an extra CRDT operation embedded in the PPM version.

### Why this matters

**Deploying a PPM's empty .rm blob to an RM1 causes the RM1 to render pages at PPM dimensions.** The result is broken rendering -- strokes appear at the wrong scale, the page is misaligned, and the user experience is completely wrong.

Critically, **the RM1 does NOT auto-convert PPM .rm files to its native format.** It trusts whatever .rm data is present and renders accordingly. This means deploying the wrong empty .rm file is not a recoverable error -- the page is simply broken until the .rm file is removed or replaced.

The safe strategy:

- **For PPM**: always deploy the correct 423-byte empty .rm file with each page. The PPM will not create correct .rm files on its own for deployed notebooks.
- **For RM1/RM2**: do NOT deploy .rm files for empty pages. Let the device create them natively on first access. The device reliably generates correct 408-byte empty .rm files.
- **For Paper Pro**: unknown. If you have one, please help us find out (see below).

## CRDT Format Details

The notebook format uses CRDTs (Conflict-free Replicated Data Types) extensively, which is how reMarkable handles cloud sync and multi-device editing without conflicts.

### Timestamps

CRDT timestamps are strings in the format `"replicaId:sequenceNumber"`:

```
"1:42"    -- replica 1, sequence 42
"3:108"   -- replica 3, sequence 108
```

### Replica IDs

- The device uses **replica 1** for its own native operations
- When the device ingests deployed content (e.g., from our tools), it rewrites our replica 1 references to its own replica ID during the next sync cycle
- This means you can safely use replica 1 when constructing content for deployment

### Device-created timestamps

When the device creates or modifies a page, it adds a `"modifed"` timestamp field to the page's CRDT metadata. Note the typo -- it is `"modifed"` with one 'i', not `"modified"`. This is a genuine typo in the firmware that has persisted across versions. Do not "fix" it in your tools.

### Fractional page ordering

Pages in `cPages` use fractional indexing for ordering, encoded as strings:

- **`"ba"` through `"bz"`**: positions 0-25
- **`"caa"` through `"czz"`**: positions 26-701

This allows inserting pages between existing pages without reindexing. A new page between `"ba"` and `"bb"` could be `"baN"` (midpoint).

## Layer Name Localization

The `.rm` binary format embeds layer names as strings, and these are **locale-dependent**. A device set to English will write `"Layer 1"` into the binary, while a device set to Spanish will write `"Capa 1"`.

This means:

- Empty `.rm` files from devices with different locale settings will have **different binary content** even if both are "empty"
- Byte-for-byte comparison of .rm files across devices is unreliable for determining equivalence unless locale is controlled for
- When constructing empty .rm files programmatically, you need to pick a locale (English is the safe default for the hacking community)

This is one more reason not to deploy empty .rm files cross-device -- even the text encoding inside them can differ.

## Device Codenames

The internal codenames for each device model can be read from `/sys/devices/soc0/machine`:

| Codename | Model | Machine String |
|----------|-------|----------------|
| rm | reMarkable 1 | `"reMarkable 1.0"` |
| rm | reMarkable 2 | `"reMarkable 2.0"` |
| rmPP | Paper Pro | `"reMarkable ferrari"` |
| rmPPM | Paper Pro Move | `"reMarkable Chiappa"` |

Note that RM1 and RM2 share the `rm` codename for template and notebook purposes -- they have identical display dimensions and coordinate systems.

The codename `ferrari` for Paper Pro and `Chiappa` for Paper Pro Move are the internal project names used during development.

## Pristine Detection

To determine whether a page has been written on, check the `.rm` file size:

### Known empty .rm sizes

| Device | Empty size |
|--------|-----------|
| RM1/RM2 | 408 bytes |
| PPM | 423 bytes |
| Paper Pro | Unknown |

### Finding edited pages

Pages with user strokes will have .rm files significantly larger than the empty size. For PPM:

```bash
# Find all pages with user content in a notebook
find {uuid}/ -name '*.rm' -size +423c
```

For RM1/RM2:

```bash
find {uuid}/ -name '*.rm' -size +408c
```

A page with no corresponding .rm file has never been opened on the device. A page with an .rm file at exactly the empty size has been opened but not drawn on. A page with an .rm file larger than the empty size has user content.

## Investigation Methodology

These findings are based on hands-on SSH investigation of a Paper Pro Move running firmware **3.26.0.68**. The methodology:

1. **SSH access**: direct SSH into the device as root
2. **Binary comparison**: `diff` and `xxd` analysis of .rm files from different devices and different locales
3. **Controlled deployment experiments**: deploying notebooks to both PPM and RM1 with and without pre-deployed .rm files, then observing rendering behavior
4. **Exhaustive .content inspection**: examining all 40 notebooks on the PPM to confirm the universal 1404x1872 coordinate space
5. **rsync to local**: copying files to `/tmp` on a development machine for analysis, because BusyBox `grep` on the device is painfully slow for binary inspection

### Key experiment: cross-device .rm deployment

The most revealing experiment was deploying a notebook with PPM-native empty .rm files to an RM1. The RM1 rendered pages at PPM dimensions -- definitively proving that the .rm binary encodes device-specific information and that the RM1 trusts whatever .rm data it receives without conversion.

## Help Wanted: Paper Pro Testing

**We need Paper Pro (rmPP, "ferrari") owners to help complete this documentation.**

The Paper Pro is the one device we have not been able to test directly. Several critical questions remain unanswered:

### What we need

1. **Empty .rm file capture**: Create a new notebook on your Paper Pro, open the first page (just view it, do not draw), then SSH in and grab the .rm file:
   ```bash
   # Find your notebook's UUID (check .metadata files for the name)
   cat /home/root/.local/share/remarkable/xochitl/{uuid}.metadata

   # List the page .rm files and their sizes
   ls -la /home/root/.local/share/remarkable/xochitl/{uuid}/

   # Copy the .rm file off the device
   scp root@remarkable:/home/root/.local/share/remarkable/xochitl/{uuid}/{pageId}.rm ./pp-empty.rm
   ```
   Share the file and its size. We expect it to be close to 408 or 423 bytes, but the exact size and content matter.

2. **Deployed notebook rendering**: If you are comfortable deploying test notebooks, try deploying one with and without pre-deployed .rm files. Does the Paper Pro create correct .rm files on its own (like RM1), or does it need them pre-deployed (like PPM)?

3. **Locale testing**: If your Paper Pro is set to a non-English locale, the layer name in your empty .rm file will be especially valuable for confirming the localization behavior.

### How to share

Open an issue on this repository with the tag `paper-pro-testing`, or reach out to the maintainers directly. Even a simple "my empty .rm file is X bytes" is valuable data.

The reMarkable hacking community has always moved forward through collective reverse-engineering. Every data point helps.
